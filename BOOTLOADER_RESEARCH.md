# ABL и варианты загрузки

## Доказательства по установленному ABL

Сохранённый `reports/abl-readonly.bin` прочитан без записи с раздела ABL. SHA-256: `0a4150904406911143aadff53f65c38326d5aaa4ca2e9bfa948c8f61ec6d0593`.
Из его UEFI volume извлечён ARM64 PE: SHA-256 `5c3a39204a7a2ac6a8eae96952393ceab94fae81112f560fdad202958d0c3a9c`.

Найдена не только строковая таблица, но и исполняемый цикл регистрации:

```text
0x35eb0: adrp x21, #0xbc000
0x35eb8: add  x21, x21, #0xe18
0x35ebc: cmp  x20, #0x1a0
0x35ec4: add  x8, x21, x20
0x35ec8: ldp  x0, x1, [x8, #0x10]
0x35ecc: bl   #0x3626c
0x35ed0: add  x20, x20, #0x10
```

Он регистрирует 0x1a0/16 = **26 обработчиков** из таблицы 0xbce28..0xbcfb8. В ней есть download, flash, erase, getvar, continue, reboot, reboot-recovery, reboot-fastboot и OEM-команды, но нет `boot`. Полный список — `reports/abl-command-table.txt`; xrefs и инструкции — `reports/abl-v2-xrefs.txt`.

Вывод: штатная команда **fastboot boot в исследованном ABL не зарегистрирована**. Это существенно сильнее прежнего вывода только по strings. Ответ работающего bootloader на команду не проверялся: телефон не перезагружался. Возможность отдельного скрытого протокола не объявляется доказанной; оснований использовать его не найдено.

В [открытом Qualcomm-производном FastbootCmds.c](https://github.com/SHIFTPHONES/android_bootable_bootloader_edk2/blob/sos-3.x/QcomModulePkg/Library/FastbootLib/FastbootCmds.c) CmdBoot и его регистрация зависят от build macro ENABLE_BOOT_CMD. Этот исходник помогает объяснить устройство таблицы, но не является точным исходником установленного Xiaomi ABL. Unlock не добавляет скомпилированные без этой команды обработчики.

`continue` запускает существующий boot-раздел: не означает запуск download buffer. `download` лишь принимает данные и не обеспечивает переход на них. Fastbootd также не заменяет bootloader loader.

## Остальные временные способы

| Путь | Что установлено | Решение |
|---|---|---|
| fastboot boot | Нет зарегистрированного обработчика в текущем ABL | Не рассчитывать на этот путь |
| kexec из TWRP | Из реального `/proc/config.gz`: `# CONFIG_KEXEC is not set` | Текущий TWRP не может выполнить обычный kexec |
| Новый recovery с kexec | Потребовал бы предварительно загрузить/записать другое recovery; переход драйверов SM6115 также не проверен | Не входит в первый тест, TWRP сохраняется |
| UEFI/lk2nd/другой ABL | Подтверждённого временного пути для установленной конфигурации не найдено | Не изменять загрузчик |
| EDL/engineering ABL | Иной уровень вмешательства и восстановления | Исключён |
| ARM64 переходник в boot image | Собран и проверен офлайн, но нужен путь запуска Android boot image | Подготовлен для согласуемого теста через boot |

Поиск не дал воспроизводимого подтверждённого временного запуска mainline для **Redmi 9T NFC lemon с этим ABL и этим TWRP**. Инструкции для Xiaomi Mi 9T/davinci неприменимы: это другое устройство. Статус [проекта Mu-Qcom](https://github.com/MoonisReal/Mu-Qcom/blob/main/Status.md) также не используется как доказательство рабочего временного пути.

## DTBO в ABL

В функции выбора DTB найден ALL_BITS test 0x19f84..0x19f94 и запись skip flag по 0xc1910 после совпадения. Полный mask — 0x35555555550000. ReadDtbFindMatch находится по 0x1a0e0. Прямой путь с metadata-only не принят из-за несогласованности 16 required PMIC model bits и 15-элементных массивов. Объяснение и данные эмуляции — `DTBO_COMPATIBILITY.md`.

v2 не использует эту ветку, не подделывает match flags и не изменяет ABL. Для ABL остаётся штатная stock DTB/DTBO пара. Замена дерева выполняется уже нашим кодом в RAM, перед штатным входом в Linux.

## Что остаётся проверить на телефоне

ABL должен принять unsigned образ в уже разблокированном состоянии, распаковать Image и передать управление переходнику по ARM64 protocol. Это пока не проверено. У сохранённого vbmeta flags=0; никаких AVB-изменений не сделано. При отказе AVB тест прекращается, исходный boot восстанавливается. Отключение проверки не является частью плана.

Возможная граница неуспеха: отказ ABL до entry; guard переходника; запуск ядра до init; init без USB/экрана. Эти случаи различаются по фактическим логам, а не по логотипу. Сценарий — `FIRST_BOOT.md`.

## Воспроизведение исследования

`scripts/inspect-abl.py` извлекает таблицу из сохранённого PE, `abl-xrefs.py` находит ссылки, `disasm-abl.py` выводит заданные диапазоны, `emulate-abl-match.py` исполняет actual selector с заменёнными UEFI API. Дополнительные Python-модули лежат локально в `tools/uefi-deps`; ABL на телефоне не выполняется этими скриптами.
