# Touchscreen — первая живая проверка

7 ноября 2026. Run: `logs/touchscreen-first-live/20261107T180106Z/` (UTC). Разрешён один эксперимент с r2/CS0 и восстановление перезагрузкой при необходимости. Выполнен только живой preflight; до активного эксперимента не дошли.

**Первое реальное касание не получено. GENI/Novatek не загружались, SPI-обмена и открытия touch evdev не было.** Остановка связана с конкретным live результатом проверки VDDIO, не с повторением офлайн-матрицы или отсутствием разрешения на reboot.

## Доступ и восстановление

- SSH с существующей проверкой host key работает через USB NCM192.168.77.1/30↔192.168.77.2/30.
- COM4 открыт эксклюзивно; получены собственный marker, версия ядра и boot ID, затем порт закрыт. После preflight COM4 вновь доступен.
- Linux `7.4.0-rc1-lemon-bringup-v8b`, boot ID `a03c6763-1c3d-434c-96c0-57d9d8610652`, tty1. DRM card0/FD610 render node присутствуют; GPU suspended.
- Контрольный v8b образ на ПК проверен:24707072байта, SHA256 `9ce181e8a6170ce8773a923f03dd10f5edb405d1990fa09b4f4bc12f2e59a610`.
- Устройство `/dev/sde49` проверено по `PARTNAME=boot`. Первые24707072байта прочитаны и дали тот же SHA256. Поэтому сохранённая загрузочная v8b совпадает с boot-разделом; путь `/sbin/reboot` существует. Перезагрузка не понадобилась и не выполнялась. Способ возврата не испытывался дополнительным reboot ради проверки.
- GNOME не запускался. Пользователь подтвердил, что на LCD продолжает отображаться текстовая консоль.

## Точный этап остановки

Текущий provider найден по имени l9, а не выбран только по историческому номеру. В этой загрузке:

```text
cat /sys/class/regulator/regulator.11/name       → l9
cat /sys/class/regulator/regulator.11/state      → disabled
cat /sys/class/regulator/regulator.11/microvolts → 1800000
cat /sys/class/regulator/regulator.11/num_users  → 0
```

Команды чтения завершились успешно; это не exit-code ошибка. Остановлен следующий шаг — регистрация GENI, способная переключить SPI pads и затем подавать clock/CS/data в NT36672A.

По уже проверенным stock DTB L9 является touch_vddio и одновременно LCD vddio; LAB/IBB также общие. Включать/выключать эти rails пользователь не разрешал.

**Показание disabled не является доказательством физического отсутствия питания.** Проверен actual mainline `drivers/regulator/qcom_smd-regulator.c`: `rpm_reg_is_enabled()` возвращает `vreg->is_enabled`, а `rpm_reg_get_voltage()` — `vreg->uV`. Это cache driver state, а не чтение напряжения с платы. Настроенные1800000 также не подтверждают физическое наличие1,8V. Возможно питание, удерживаемое другим RPM client/унаследованным состоянием; оно не подтверждено этим интерфейсом.

Причина остановки: если VDDIO действительно отсутствует, активные SPI-сигналы могут питать контроллер через I/O. Без подтверждения существующего VDDIO нельзя исключить именно этот электрический риск. Здесь не утверждается, что сенсор точно обесточен, что повреждение произошло или что состояние cache равно состоянию PMIC. Общие регуляторы не переключались ради устранения неопределённости.

## Что требуется для продолжения

Нужно подтвердить **уже существующее питание VDDIO сенсора до переключения SPI**, без изменения shared LCD rails: надёжный аппаратный status с документированным смыслом либо контролируемое высокоомное измерение на подтверждённой точке питания квалифицированным специалистом. Cache RPM framework и работающая картинка LCD этого отдельно не измеряют.

После такого подтверждения остаётся выбрать минимальную CS0 runtime registration и выполнить только ранее согласованный r2 путь без reset/upload. Результаты этой проверки не дают основания подставлять FW6, включать L9/LAB/IBB или применять отозванный DTB. Не выполняется повторная попытка автоматически.

Это отчёт **о preflight, остановленном до первого активного SPI-теста**, а не об успешном или неуспешном probe NT36672A. Причина отказа самого контроллера пока не известна, потому что команд ему не отправляли.
