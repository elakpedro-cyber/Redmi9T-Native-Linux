# REFGEN и VDD_MX на SM6115/Bengal — техническое заключение

**Stage C/B остаётся NO-GO.** На Redmi 9T NFC подтверждён программный запрос REFGEN у DSI Host, но доступные материалы не устанавливают отдельный REFGEN-блок, его владельца и режим холодного старта. По VDD_MX подтверждены ресурс, активный уровень и отличие штатного выключения от mainline. Подготовлен отдельный отключённый DTB для проверки привязки. Рабочий v8b и GNOME не изменены.

## 1. Что говорит код о REFGEN

- **Оригинал этого аппарата.** В stock boot+DTBO и архивном TWRP FDT узел host DSI0 `0x05e94000` перечисляет `refgen` в `qcom,core-supply-entries` с нулевыми voltage/load. У него нет `refgen-supply`. В TWRP запрос вернул dummy. Сообщение о dummy `gdsc` у PHY относится к другому ресурсу. Привязка TD4330 показывает использование профиля, а для cold start, физического reference или штатного выключения отдельного подтверждения нет. [Воспроизводимый аудит](logs/display-safety-gate/evidence.json) · [TWRP](logs/v8-authorized/twrp-dmesg-before.txt#L855) · [Qualcomm Bengal DTS](https://android.googlesource.com/kernel/msm-extra/devicetree/+/refs/heads/android-msm-redbull-4.19-android12/qcom/bengal-sde.dtsi)
- **Xiaomi downstream.** `dsi_ctrl.c` парсит core entries в группу digital, ctrl entries — отдельно в host_pwr. Получает каждый supply по имени, а power path вызывает общий `dsi_pwr_enable_regulator()`. Это обычный regulator consumer. Сопоставленный исходник не содержит специальной ветки программирования REFGEN. PHY `dsi_phy.c` независимо получает `gdsc` и записи `qcom,phy-supply-entries`, где на этом аппарате описан VDD_MX. [DSI ctrl Xiaomi](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/02ca1a919564a9b176a79cce09c40977f833e9ac/techpack/display/msm/dsi/dsi_ctrl.c#L741) · [DSI PHY Xiaomi](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/02ca1a919564a9b176a79cce09c40977f833e9ac/techpack/display/msm/dsi/dsi_phy.c#L151) · [Цепочка вызовов](logs/refgen-sm6115/driver-evidence.txt)
- **Mainline, используемый v8b.** Shared host config v2.4 получает `vdda` и `refgen` и использует их через bulk regulator API. `0x05e94000` встречается в общей конфигурации нескольких SoC. PHY compatible `qcom,dsi-phy-14nm-2290` сам REFGEN regulator не запрашивает. Это подтверждает местоположение consumer в Linux, а электрическая необходимость отдельного REFGEN для именно этой 14-нм реализации остаётся неизвестной. [DSI host config](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/msm/dsi/dsi_cfg.c) · [14-нм PHY](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/msm/dsi/phy/dsi_phy_14nm.c) · [Вырезка pinned tree](logs/refgen-sm6115/adjacent-phy.txt)

Серия не добавляет SM6115 provider. Публичная схема J19S не привязывает `PMI_REF_BYP` к DSI. Ни сходство регистров PHY, ни имя reference, ни наличие firmware framebuffer не доказывают владельца. Нужен SM6115-специфичный register map с семантикой и порядком enable/disable либо доказательство управления firmware с воспроизводимым cold handoff и подтверждением того, какие стадии разрешено брать под управление Linux. До этого остаётся [офлайн guard](display-v8/sm6115-refgen-required.patch), проверяющий реальный handle перед probe. ### Что точно можно различить на SM6115

| Ресурс | Назначение и доказательство |
|---|---|
| REFGEN | Аналоговое reference supply на тех Qualcomm SoC, где это документировано. На SM6115 подтверждено только имя у consumer. Адрес, конфигурация, владелец и физическая необходимость неизвестны. |
| VDD_MX | Уровень общего PM6125 S5 для домена MX, запрос через RPM SMD `rwmx:0`. Stock PHY просит этот ресурс отдельно. |
| XO | Тактовый вход PHY `ref`, DTS указывает RPM XO, расчёт VCO использует 19,2 МГц. Это clock framework; ещё один вход `iface` — DISPCC AHB. |
| VDDA host | Отдельное аналоговое питание через PM6125 L18, DT описывает 1,232 В. |
| PHY/PLL MMIO | Mainline SM6115 DT задаёт PHY common `0x05e94400`, lane `0x05e94500`, PLL `0x05e94800`. XML и драйвер используют `VREF_CFG1` по PLL offset `0x5c`, `RESET_SM_READY_STATUS` по `0xcc` (LOCK bit 5, READY bit 0), `PLL_CNTRL` по common offset `0x48`. Это регистры программирования и контроля 14-нм PLL. Xiaomi PHY v2.0 также пишет локальный `LDO_CNTRL` и lane `VREG_CNTRL`. Ни один из этих путей не идентифицирует отдельный REFGEN provider. |

[SM6115 DTSI](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/qcom/sm6115.dtsi) · [Регистр PLL](https://github.com/torvalds/linux/blob/master/drivers/gpu/drm/msm/registers/display/dsi_phy_14nm.xml) · [Xiaomi PHY v2.0](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/02ca1a919564a9b176a79cce09c40977f833e9ac/techpack/display/msm/dsi/dsi_phy_hw_v2_0.c)

## 2. VDD_MX через PM6125 S5

1. Stock и TWRP DT разрешают `vdda-0p9-supply` в `pm6125_s5_level` под RPM resource `rwmx:0`. `qcom,use-voltage-level` переключает downstream regulator на ключ `vlvl`. Xiaomi `rpm_vreg_set_voltage()` ставит минимум запроса за вычетом offset и проверяет максимум. Для stock PHY **256 (NOM)** — запрошенный уровень, **416 (TURBO_NO_CPR)** — верхняя граница, **16 (RETENTION)** — запрос перед disable. Downstream может агрегировать запросы других потребителей, поэтому значение, реально удерживаемое RPM, нельзя вывести из одного DT. Значения — corner IDs. [Stock phandles](logs/display-safety-gate/evidence.json) · [Qualcomm regulator DT](https://android.googlesource.com/kernel/msm-extra/devicetree/+/refs/tags/android-s-v2-beta-1_r0.5/qcom/bengal-regulator.dtsi) · [Xiaomi RPM SMD driver](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/02ca1a919564a9b176a79cce09c40977f833e9ac/drivers/regulator/rpm-smd-regulator.c#L807)
2. Mainline `SM6115_VDDMX` — тот же ресурс `rwmx:0` с `KEY_LEVEL=vlvl`, управляемый `rpmpd`/genpd. Поэтому активный уровень описывается у PHY через `power-domains = <&rpmpd SM6115_VDDMX>` и `required-opps = <&rpmpd_opp_nom>`. Binding 14nm допускает обе ссылки, PM core получает default OPP при присоединении, PHY уже использует runtime PM. Для SM6125 в upstream есть пример того же способа, а выбор уровня для lemon выведен из его stock DT и драйвера. [Mainline rpmpd](https://github.com/torvalds/linux/blob/master/drivers/pmdomain/qcom/rpmpd.c) · [PHY binding](https://github.com/torvalds/linux/blob/master/Documentation/devicetree/bindings/phy/qcom,dsi-phy-14nm.yaml) · [SM6125 DTSI](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/qcom/sm6125.dtsi)
3. **Различие в lifecycle.** Platform probe может включать присоединённый домен, generic runtime suspend снимает vote до 0, resume восстанавливает его. Downstream запрашивает RETENTION перед regulator disable. Кроме того, RPM power-on и перенос vote при restore идут через разные вызовы. До отдельной проверки не доказаны безопасный порядок переходов при cold start, suspend/resume, rollback и совместное владение MX с другими потребителями. Дополнительный RPM-регулятор, дублирующий `rwmx:0`, не требуется для описания активного vote. [Genpd](https://github.com/torvalds/linux/blob/master/drivers/pmdomain/core.c) · [Точная вырезка](logs/refgen-sm6115/domain-details.txt)

Собран [review overlay](display-v8/sm6115-dsi-phy-mx-review.dts) и [отключённый DTB](logs/refgen-sm6115/sm6115-dsi-phy-mx-review.dtb). На его основе можно проверять граф, bindings и OPP. В нём только у отключённого PHY добавлены две ссылки, REFGEN provider отсутствует. Аудит проверяет домен 3, OPP 256, неизменность всех остальных узлов и отклоняет активный PHY. Установка в boot не предусмотрена. [Сборка](scripts/build-dsi-phy-mx-review.sh) · [Результаты](logs/refgen-sm6115/dtb-validation.txt)

## 3. Электрические ворота

| Класс | Открытые вопросы и критерии |
|---|---|
| Анализ исходников | Найти доказательство REFGEN, сопоставить genpd off/RETENTION с подтверждёнными требованиями PHY и определить точный порядок rollback. Закрыто сопоставление VDD_MX и его NOM. Кодовый аудит не измеряет питание. |
| Пассивный осмотр обесточенной платы | PCB/assembly revision, маркировки flex/DDIC и U2732, графический лист/boardview, CN2701 pin 1 и подходящая reference-точка. Подтвердить отдельные трассы VSP/VSN, VDDIO, HWEN, LED_A и проверить, как разведён `PMI_DISP_HW_EN`. Текстовый OCR не назначает контакт. |
| Измерения специалистом под питанием | Отдельный согласованный план с документированными пределами модуля, interposer, двумя независимыми высокоомными каналами с допустимым common-mode для отрицательной шины и проверенной аварийной остановкой. Нужны исходный handoff, включение, штатный off, физический разряд и безопасно определённый сценарий отказа. Тестировать только после пассивной сверки и согласования плана. |

Точные цепи по схеме и stock DT: **LAB → PMI632 LCDB LDO → VDISP_P_OUT → LCD_VSP → CN2701**, **IBB → PMI632 LCDB NCP → VDISP_M_OUT → LCD_VSN → CN2701**. Отдельно измерять PM6125 L9/VDDIO и фиксировать HWEN/LED_A, чтобы обнаружить обратное питание и исключить подсветку из bias-теста. Удерживать обе bias-трассы на двух каналах одновременно с общим временным маркером. Зафиксировать полярность, порядок, ramp, overshoot, ripple, стационарные уровни и время до документированного порога off для **каждой** шины. TWRP показывает цифровой readback модуля 5,5 В; он не задаёт допустимых пределов панели. Порог разряда, остаточное напряжение и время off пока неизвестны. Не использовать LED_A как bias и не подавать внешнее напряжение в измерительные точки. [Схема J19S, листы 19 и 27](https://www.scribd.com/document/613010966/Xiaomi-Redmi-9T-Schematic-pcb) · [Карта аппарата](REDMI9T_DISPLAY_HARDWARE_MAP.md) · [GO/NO-GO](DISPLAY_FIRST_LIGHT_GO_NO_GO.md)

Контрольные boot v8b, GNOME RDP и GNOME Desktop сверены по прежним SHA-256. Действий с телефоном не выполнялось. [Хеши](logs/refgen-sm6115/control-sha256.txt)
