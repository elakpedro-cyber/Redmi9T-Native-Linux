# Тестовая загрузка — только после отдельного разрешения

Этот документ относится к v1. Актуальный план для v2 — `FIRST_BOOT.md`; вывод по отсутствию fastboot boot усилен анализом исполняемого цикла регистрации в `BOOTLOADER_RESEARCH.md`.

Ни одна команда этого документа автоматически не выполнялась.

## Ограничение установленного ABL

В извлечённом с телефона ABL таблица fastboot содержит 26 команд и не содержит `boot`.
Сохранены `reports/abl-command-table.txt` и исходная копия ABL. Это сильный статический признак отсутствия `fastboot boot` в данной сборке; ответ загрузчика в fastboot пока не проверен.
Не следует рассчитывать на временный запуск. Нельзя проверять это прошивкой или сменой ABL.

## Согласованный первый этап

1. Проверить SHA-256 резервных копий по `reports/backup-sha256-before.json`.
2. Подготовить доступ к TWRP сочетанием Power + Volume Up и достаточный заряд.
3. Только после разрешения перевести телефон из TWRP в bootloader. Это отдельное действие, не часть сборки.
4. В Windows PowerShell, из исходного каталога platform-tools_r37.0.1-windows, запросить:

```powershell
.\platform-tools\fastboot.exe devices
.\platform-tools\fastboot.exe getvar product
.\platform-tools\fastboot.exe getvar is-userspace
.\platform-tools\fastboot.exe getvar version-bootloader
.\platform-tools\fastboot.exe getvar max-download-size
.\platform-tools\fastboot.exe oem device-info
```

Нужен именно bootloader fastboot (`is-userspace: no`), а не fastbootd.
Стандартного read-only запроса «поддерживает ли boot» нет. Наличие команды в справке программы на ПК ничего не доказывает.

При отдельном согласии проверить временную загрузку уже сохранённого, известного рабочего recovery:

```powershell
.\platform-tools\fastboot.exe boot .\platform-tools\Redmi9T_Backup\recovery.img
```

`unknown command` означает остановку этого пути. Другая ошибка не доказывает ни поддержку, ни отсутствие поддержки: сохранить полный вывод. Не выполнять `flash`, `erase`, AVB-команды или замену загрузчика.

## Только если временная загрузка действительно подтверждена

Текущий дополнительный СТОП: stock overlay #0 совместим со stock base DTB, но не с mainline (`FDT_ERR_NOTFOUND`). Перед любым тестом Linux необходимо отдельно подтвердить безопасный путь выбора полного DTB без применения этого overlay либо разработать согласованное совместимое решение. Стирание DTBO не является решением в рамках текущего задания.

Только после устранения обоих препятствий, проверки TWRP и отдельного согласования теста Linux можно использовать приведённую ниже команду. Сейчас это справочный пример, а не рекомендация запускать готовый образ. Формат образа проверен, но размещение mainline в памяти и его запуск ещё не подтверждены.

```powershell
.\platform-tools\fastboot.exe boot .\Redmi9T-Native-Linux\artifacts\boot-linux-test.img
```

Не добавлять `--disable-verity`, `--disable-verification`, `-w`; не стирать dtbo.
Если загрузчик отвергнет образ по AVB или DTB, остановиться и сохранить сообщение. Любое изменение AVB требует отдельного согласования.

## Логи

Экран: ожидаемый маркер `Redmi9T Native Linux: initramfs reached`, если simpledrm сохранит framebuffer и подсветку. Нативный драйвер панели не включён; чёрный экран сам по себе не доказывает остановку ядра.

USB: init пытается создать только ACM serial gadget, VID:PID `1d6b:0104`. На Windows проверить появление нового COM-порта в диспетчере устройств; подключить терминал к нему, 115200 8N1, без flow control, нажать Enter. Не путать старое TWRP USB-устройство с новым Linux gadget.

Из оболочки:

```sh
uname -a
cat /proc/cmdline
dmesg
cat /run/usb-setup.log
ls /sys/class/udc
cat /sys/class/udc/*/state
```

Работа USB считается подтверждённой только после нового USB-перечисления, открытия консоли и получения вывода. ADB в этом initramfs отсутствует. USB-сеть не настроена и не проверена.
Ранняя USB-консоль до инициализации драйверов невозможна этим способом; UART требует отдельного аппаратного исследования.
Ramoops предусмотрен upstream DT: после сбоя и тёплого возврата в TWRP можно прочитать `/sys/fs/pstore`, если recovery поддерживает тот же регион. Его сохранность пока не проверена; при отключении питания логи могут пропасть.

## Если fastboot boot недоступен

Остановить тест. Возможные следующие работы: изучение kexec в текущем TWRP (наличие CONFIG_KEXEC/KEXEC_FILE и совместимость перехода) либо согласованный эксперимент с записью только boot и последующим восстановлением исходного boot.img при сохранении recovery.
Оба варианта требуют нового плана и разрешения; текущий проект их не выполняет. Kexec не считается рабочим и не предлагается к запуску вслепую. Замена ABL, lk2nd, стирание DTBO и отключение AVB в этот план не входят.
