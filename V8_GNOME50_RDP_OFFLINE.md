# GNOME 50 и RDP для v8b

Актуальный образ с исправлением ветви SIT, privilege-drop preflight и проверкой готовности PipeWire имеет размер 318 881 792 байта и SHA-256 `5121814c02cebd7168369c02e5737f09985636d69e6f9151a7c39b8f87351491`. Исходный хеш ниже относится к предыдущей сборке. [Диагностика и регрессия](V8_GNOME50_RDP_HARDWARE_RESULTS.md)

## Сборка

ARM64 rootfs Alpine 3.24 в gzip SquashFS, 318 877 696 байт. SHA-256 `699914d5ff689f3be91405f1bcb7490dbc897cbcd20ba7510f72ab9696d094b9`. Внутри GNOME Shell 50.3, Mutter 50.2 с проверкой FD610, GNOME Session 48.0, GNOME Remote Desktop 50.1, FreeRDP 3.32.2, GTK 4.22.4, Libadwaita 1.9.2, dconf 0.49.0, Console 50.0, Settings 50.3, PipeWire 1.6.8 и WirePlumber 0.5.15. Приватные ключи, пароли, machine-id и файлы тестовой сессии исключены. Извлечённая библиотека Mutter побайтово совпала с ранее испытанным FD610-бинарником. Этот абзац описывает первоначальный офлайн-образ. Актуальная сборка успешно отдала кадр с физического Redmi 9T. Результаты приведены в аппаратном отчёте.

Профиль `lemon-headless` запускает настоящий Shell через GNOME Session 48. В тесте UID 1000 использовал собственные D-Bus, HOME и XDG-каталоги, а dconf активировался на пользовательской шине. Системная шина была приватной, без активации сервисов хоста. Подготовлены GSettings schemas, gdk-pixbuf, MIME, desktop, Adwaita icon и fontconfig caches и `/etc/localtime` UTC. Не все предупреждения сняты. В минимальной сессии отсутствуют GDM, colord, системный polkit, GeoClue и RTKit. В QEMU появлялось предупреждение Glycin о sandbox. Скрипты не отключают sandbox. На аппарате предстоит проверить его штатную работу.

Shell сообщил, что блокировка экрана требует GDM. Этот профиль ограничен одноразовым приватным сеансом, защищённым аутентификацией SSH и RDP. Для постоянного рабочего стола блокировку экрана нужно отдельно реализовать и проверить. Пользователь `lemon` сохраняет заблокированный login, а Console запускает `/bin/sh` явно через собственную запись приложения.

## Два сбоя grdctl и режим OpenRC

1. В `grdctl` из GRD 50.1 отсутствует проверка результата `getpwnam(GRD_USERNAME)`. Учётной записи `gnome-remote-desktop` не было. GDB зафиксировал SIGSEGV на AArch64 `ldr w1, [x20, #16]`, смещение в ELF `0x4574`, сразу после `getpwnam` и `geteuid`. QEMU strace показывает адрес обращения `0x10`. После создания заблокированной системной учётной записи исходная команда завершилась успешно. Пользователь рабочего стола — отдельный `lemon`, UID 1000. [Исходник grdctl 50.1](https://github.com/GNOME/gnome-remote-desktop/blob/50.1/src/grd-ctl.c)
2. При двух строках в stdin первый `GDataInputStream` считывает обе строки, затем уничтожается. Второй читает EOF. Код печати ошибки обращается к пустому `GError`, SIGSEGV по адресу `0x8`. В syscall-журнале есть чтение обеих строк за один вызов и EOF при следующем. Повтор с именем пользователя в аргументе и единственной строкой пароля в stdin проходит. Реальный пароль не передаётся в argv и не журналируется. [Исходник grdctl 50.1](https://github.com/GNOME/gnome-remote-desktop/blob/50.1/src/grd-ctl.c)
3. Alpine собирает GRD с `-Dsystemd=false`, но `grdctl --headless rdp enable` всё равно запросил `org.freedesktop.systemd1` и завершился ошибкой. В приватной сессии выставляется ключ `org.gnome.desktop.remote-desktop.rdp.headless enable` через GSettings, затем штатный daemon запускается вручную. TLS, NLA и парольная аутентификация RDP сохраняются. Headless GRD на этой системе без TPM использовал свой штатный GKeyFile backend. Файлы dconf, TLS и `credentials.ini` наблюдались с режимом 0600 и владельцем UID 1000. В будущем на телефоне они будут находиться в приватном tmpfs. Secret Service нужен для других режимов GRD и приложений, этот headless путь с ним не связывали. [Alpine APKBUILD](https://github.com/alpinelinux/aports/blob/3.24-stable/community/gnome-remote-desktop/APKBUILD), [GNOME Remote Desktop 50.1](https://github.com/GNOME/gnome-remote-desktop/blob/50.1/README.md)

## QEMU ARM64

В QEMU user-space с Xvfb/FreeRDP сервер в loopback-only namespace принимал RDP с TLS и NLA, клиент проверял SHA-256 отпечаток одноразового сертификата. С PipeWire/WirePlumber, контролируемым software EGL только на ПК и единственным виртуальным монитором GRD получен настоящий кадр GNOME 480×720. После исправления TZ первый непустой кадр приходил за 7,5–8,5 с от запуска клиента, включая подключение и готовность Shell. Этот показатель не является задержкой кадра на готовом рабочем столе.

В финальном прогоне из распакованного SquashFS нажатие мыши и клавиша X дошли по RDP до диагностического GTK Wayland-клиента. Тест проверял два независимых события в журнале приложения, а RDP-клиент сохранил кадр этого окна. GTK-клиент использовал Cairo только в офлайн-диагностике. Управление окнами Console/Settings через RDP пока не подтверждено. [Кадр теста ввода](logs/v8b-gnome50-rdp/interactive-input-cairo/rdp-input-probe.png)

Дополнительный SIGSEGV при подключении локализован в `strcmp → libwinpr3 → GetDynamicTimeZoneInformation → GetTimeZoneInformation → freerdp_settings_new → freerdp_peer_context_new_ex`. В изолированном вызове той же функции без TZ процесс завершался с 139, с `TZ=Etc/UTC` функция возвращала 1. Явная зона задана только для GRD, после этого проверено получение кадра. До первого кадра Shell может показывать чёрный экран. При отключении последнего виртуального монитора Mutter под QEMU выдавал предупреждения об отсутствующем logical monitor. [WinPR timezone 3.32.2](https://github.com/FreeRDP/FreeRDP/blob/3.32.2/winpr/libwinpr/timezone/timezone.c)

В ядре v8b нет CONFIG_FUSE_FS. Когда клиент подключал CLIPRDR, GRD пытался смонтировать FUSE clipboard и аварийно завершался. Отключение clipboard redirection только в клиенте позволило продолжить, оно не меняет TLS и NLA. В шаблоне `lemon-gnome.rdp` также отключено перенаправление дисков, принтеров и смарт-карт. [Условие запуска CLIPRDR в GRD 50.1](https://github.com/GNOME/gnome-remote-desktop/blob/50.1/src/grd-session-rdp.c)

Предсборка кешей исключает эту работу при старте телефона. Один монитор GRD избегает второго виртуального выхода. Формат SquashFS снижает размер переноса до примерно 304 МиБ. Рабочее дерево при распаковке требует около 849 МиБ tmpfs. Пиковый PSS в прогонах из распакованного выпуска достигал 1 465 665 KiB (около 1,40 ГиБ), включая QEMU. Старые замеры GPU-only на телефоне нельзя переносить на RDP. FD610, расход RAM на телефоне, плавность, частота кадров, доставка кадров и энергопотребление в интерактивном режиме остаются предметом аппаратной проверки.

## Следующий тест

Скрипты в `userspace/gnome50-v8b/`: `run-rdp-fd610.sh`, `start-gnome-rdp-session.sh`, `start-rdp.sh`, `rdp-stream.sh` и `lemon-gnome.rdp`. Используется статический namespace-watchdog r2, уже проверенный в аппаратном GPU-only тесте. Запускатель RDP ждёт аппаратного FD610 и D-Bus Mutter, прежде чем открывать сервер. В этом режиме GRD сам создаёт монитор после подключения. Ожидание полной готовности Shell до подключения создало бы циклическую зависимость.

1. После отдельного разрешения и включения телефона сверить версию v8b, закрепить текущий SSH host key через COM4, проверить NCM, свободную RAM и существующий renderD128. Если GPU не подготовлен, остановиться. Зафиксировать GPU runtime PM, dmesg, UFS и блокировку MDSS.
2. На ПК распаковать проверенный SquashFS и подготовить tar для SFTP. На телефоне распаковать его только в новый закрытый каталог `/tmp/lemon-gnome50/root` в tmpfs. Сверить SHA-256 после передачи. Передать одноразовый сертификат для localhost, его ключ и учётные данные отдельно, с режимом 0600. Опубликовать на ПК только отпечаток сертификата. Стадирование завершить до начала таймера.
3. Один раз запустить r2 с лимитом до 60 с, heartbeat по SSH и приватными PID, mount и network namespaces. Внутри поднять только loopback. Подтвердить FD610, отсутствие modeset и отсутствие TCP 3389 в основной сети телефона. Записать PID namespace из журнала watchdog в защищённый `rdp.pid` после проверки, что сеть действительно содержит только lo.
4. На Windows использовать существующий `vnc-ssh.py --gnome-rdp --identity … --known-hosts …` как TCP-ретранслятор на `127.0.0.1:13389`. Проверить TLS-сертификат отдельно и открыть шаблон mstsc. Если клиент не позволяет сверить отпечаток, использовать клиент с явным pin. Проверить кадр, Activities, окно Console, Settings, ввод мышью и клавиатурой. Снять стартовую задержку, PSS, dmesg и GPU fdinfo. Прервать при программном рендерере, GPU/IOMMU fault, ошибке TLS или потере SSH.
5. Watchdog завершает namespace, после чего проверить отсутствие процессов и монтирований, удалить временные данные и TLS-материалы, проверить suspend GPU, COM4, SSH и неизменность UFS. Stage C/B остаётся NO-GO.

Телефон во время подготовки не использовался.
