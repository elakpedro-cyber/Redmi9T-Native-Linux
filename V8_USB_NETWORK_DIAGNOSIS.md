# v8b — диагностика USB NCM и SSH

**Установленная причина таймаута — на Windows отсутствует 192.168.77.1/30 и прямой маршрут USB к телефону.** USB NCM адаптер распознан и поднят. У Linux сохранены адрес и слушающий Dropbear.

|---|---|
| USB composite | VID:PID `1d6b:0106`, `MI_00` COM4 и `MI_02` NCM, оба PnP OK. |
| Windows NCM | `Ethernet 2`, `UsbNcm Host Device`, ifIndex 9, MAC `02:00:00:00:77:01`, Up/Connected, PnP problem code 0. Служба UsbNcm Running, Microsoft `usbncm.inf` 10.0.28000.3231, бинарник в DriverStore. |
| Windows IPv4 | Только `169.254.119.71/16` на USB, DHCP отключён. `192.168.77.1` отсутствует во всех IPv4 интерфейсах, у NCM нет адреса в PersistentStore. |
| Linux | v8b, UDC `4e00000.usb` configured, ACM и NCM привязаны. `usb0 UP,LOWER_UP`, carrier 1, `192.168.77.2/30`. OpenRC службы запущены, TCP `192.168.77.2:22` LISTEN. COM4 отвечает. |
| SSH | Таймаут до аутентификации. Доступность аутентификации и SFTP проверяется после возврата IPv4. Свежий публичный ключ получен по COM4 для текущей загрузки и закреплён отдельно. |

Исторический лог Stage B содержит тот же PnP instance и MAC с адресом на ifIndex 72. Сейчас 72 принадлежит WSL, USB NCM имеет 9. PnP фиксирует более поздний LastArrivalDate. Старый скрипт создавал адрес только в ActiveStore, что объясняет его отсутствие после пересоздания активной конфигурации. Журнал не фиксирует точный момент потери адреса и не позволяет отличить физическое переподключение от повторной нумерации после перезапуска. Кабель намеренно не переподключался. Найдены события установки/запуска PnP 400/410, наблюдаемый NCM без ошибки. Канал USBHUB3/Operational недоступен. ## Минимальное восстановление

1. [Restore-LemonV8bUsbIp.ps1](scripts/Restore-LemonV8bUsbIp.ps1) в режиме preflight уже подтвердил цель по VID/PID/MI, MAC, PnP и статусу. Скрипт сохраняет исходные адреса, DNS и маршруты на ПК. Если адрес или USB маршрут занят другим интерфейсом, прекращает работу. Номер интерфейса определяет каждый раз.
2. После согласования запустить скрипт с `-Apply` от администратора. Единственная операция — добавить `192.168.77.1/30` в ActiveStore указанного USB NCM. Без изменения шлюза, DNS, других интерфейсов и состояния gadget/UDC. Этот вариант следует перепроверять после следующей повторной регистрации устройства.
3. Проверить Preferred, исходный интерфейс для маршрута и ping. Использовать `StrictHostKeyChecking=yes` с публичным ключом из COM4 для текущей загрузки. Проверить Alpine/OpenRC, UFS, mounts/swap и контрольный SFTP round trip с SHA-256 исключительно через RAM `/tmp`. После закрытия SSH отдельно подтвердить COM4. При несовпадении ключа сверить текущий публичный ключ через COM4. Текущий `known_hosts` v8b из предыдущей загрузки не использовать.
4. При доступном IP и недоступном ping/TCP проверить выбор маршрута и ARP на USB, затем журналы Dropbear через COM4. Перезапуск интерфейсов, гаджета и телефона в процедуру не входит.

На момент первичной диагностики `-Apply` не выполнен. [Подготовленный pin](logs/v8b-usb-recovery/host-fingerprint.txt).

## Результат восстановления 6 ноября 2026

Повторная проверка перед записью сопоставила `USB\VID_1D6B&PID_0106&MI_02`, MAC `02:00:00:00:77:01`, Up/Connected, PnP OK и отключённый DHCP. На найденном ifIndex 9 назначен только `192.168.77.1/30` в ActiveStore. Адрес перешёл в Preferred. Повторный запуск с `-Apply` обнаружил существующий адрес и не выполнял добавление. Автозапуск не установлен.

- Ping от `192.168.77.1` к `192.168.77.2` — 3/3, менее 1 мс. TCP 22 прошёл через Ethernet 2.
- SSH по ключу с обязательной проверкой host key. `uname -a` показал v8b, Alpine 3.24.4, OpenRC default с net/sshd/health, uptime около 16 минут.
- Передача 1024 байт через SFTP по умолчанию в OpenSSH 9.5 SCP, без legacy `-O`. Файл отправлен в проверенный tmpfs `/tmp`, скачан обратно, все SHA-256 совпали с `a41863416bfa29c9bc42fdd73b21b34482d0751f2a722682c2ed68c0118ded64`. Удаление подтверждено отдельной SSH-проверкой.
- COM4 ответил после передачи, UDC configured, NCM carrier 1. UFS sda–sdf видны, дисковых mounts/swap нет, счётчики записи, discard и flush нулевые.
- Адреса, маршруты и DNS всех прочих IPv4 интерфейсов совпали до и после. Домашний Ethernet сохранил `192.168.0.51/24`, DHCP, шлюз `192.168.0.1` и прежние DNS. USB DHCP остался отключённым.

### Почему адрес исчез и как вернуть его снова

Windows сообщает о запуске 6 ноября в 06:03:22, а о регистрации NCM в 06:05:31. Историческое назначение было только в ActiveStore, записи в PersistentStore нет. Перезапуск Windows объясняет потерю адреса, даже если USB оставался подключён. Доступных данных для установления отдельного физического переподключения нет. Старый ifIndex 72 больше нельзя использовать для USB, поскольку сейчас он назначен WSL. [Снимок Windows](logs/v8b-usb-recovery/policy-store-evidence.txt) · [Microsoft NetTCPIP](https://learn.microsoft.com/en-us/powershell/module/nettcpip/new-netipaddress?view=windowsserver2025-ps).

Из каталога проекта запустить `./scripts/Restore-LemonV8bUsbIp.ps1` для preflight. При отсутствии адреса повторить команду с `-Apply` из PowerShell администратора. Скрипт заново находит интерфейс по PnP/MAC и пишет снимок и результат в `logs/v8b-usb-recovery`.
